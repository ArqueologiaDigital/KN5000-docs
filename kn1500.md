# Technics SX-KN1500 — the TLCS-900 outlier

The **SX-KN1500** (1996) is an early Technics arranger keyboard. Unlike the later
MN10300 models ([KN2400/KN2600]({{ site.baseurl }}/kn2400-kn2600/), KN6000, KN6500,
[KN7000]({{ site.baseurl }}/kn7000/)), it is built around a **Toshiba TLCS-900 (`TMP95C061`)** — the
same CPU lineage as the [SX-KN5000]({{ site.baseurl }}/system-overview/). So in the MAME work it
belongs with `kn5000.cpp`, not the MN10300 `kn7000.cpp` family.

## The ROM

A mask ROM marked **IC15** (`QSIGT3C16079`, date code 9649 = 1996) was dumped into
two 2 MB files, mapped as two logical ROMs:

| File | Region | CPU address |
|------|--------|-------------|
| `…ic15` | `prog` (program) | `0xe00000` |
| `…ic15.rest` | `rhythm` | `0xc00000` |

**The program boots coherently.** The TLCS-900/H reads its reset PC from `0xffff00`,
where `…ic15` holds a valid vector to `0xfffee0` (`jp 0xfe5f4f`); the routine at
`0xfe5f4f` is a textbook crt0 that initializes the TMP95C061's on-chip registers
(`res 7,(0x6e)`, `ld (0x6f),0xb1`, `ld (0x12),0x3b`, …). So the dump decodes as valid
TLCS-900 code.

> An earlier version of this page wrongly called the dump flawed. That verdict came
> from disassembling `0xe00000` — the ROM's *data* region, not code — and from reading
> `0xfffff0` instead of the reset vector at `0xffff00`. The data region stores its
> strings/tables in a 16-bit-per-entry format with `0xff` high bytes, which is normal
> content, not a dump artifact.

It is kept as `BAD_DUMP` only as a conservative "unvalidated" marker pending a
confirming redump; on this evidence it is very likely already a good dump.

## MAME status

A preservation **skeleton** driver (TLCS-900 `TMP95C061`, in `kn5000.cpp`) declares
the machine. The program ROMs are kept `BAD_DUMP` (a conservative "unvalidated"
marker — they do boot coherently), and the **LCD panel SVG is preserved as a ROM
asset** rendered on an `SCREEN_TYPE_SVG` screen (the Game & Watch / `hh_sm510`
pattern). Image hashes:
